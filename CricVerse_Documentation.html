1. INTRODUCTION

1.1 EXISTING SYSTEM

  • The current systems for managing local cricket tournaments, tracking team rosters, and logging live scores largely involve manual paper-based scoresheets or fragmented, disconnected mobile apps.
  • There is no centralized system that dynamically correlates live scored matches with an overarching tournament standing, player career profiles, and equipment purchases in one ecosystem.
  • Time-Consuming: Organizers must manually aggregate scores from physical sheets and calculate run-rates/averages at the end of matches.
  • Error-Prone: Physical calculation of complex metrics like Net Run Rate (NRR) and bowler economy is subject to human error and frequently causes disputes.
  • Decentralized Data: Player stats, tournament fixtures, and team management are stored on personal devices or spreadsheets, limiting accessibility.

1.2 NEED FOR THE NEW SYSTEM

Local clubs, academies, and professional leagues frequently interact with players, umpires, and fans. They accumulate massive amounts of data from game to game. The manual process of recording scores ball-by-ball, updating points tables, and managing equipment inventory is highly inefficient.

Key Drivers for the Need of a New System:

  • A robust digital solution to replace physical scoresheets and manual accounting.
  • Automated generation of career statistics and tournament standings.
  • Real-time live scoring UI that broadcasts math updates to fans instantly.
  • An integrated e-commerce store allowing players and clubs to safely purchase professional standard gear directly from the management platform.

1.3 OBJECTIVE OF THE NEW SYSTEM

  • Develop a secure, high-performance, user-friendly digital cricket management web application using Next.js and MongoDB.
  • Automate complete match orchestration with a seamless ball-by-ball logging system.
  • Provide real-time data persistence, broadcasting scores, wickets, and run rates dynamically.
  • Implement an intuitive team management dashboard to create rosters, assign captaincy, and analyze multi-format player histories.
  • Build an authentic pro-cricket store with shopping cart context APIs and secure order capabilities.

1.4 PROBLEM DEFINITION

  • Limited Accessibility: Physical scoresheets get damaged or lost. Fans cannot track away games.
  • Manual Data Entry: Tournaments require dedicated statisticians just to enter box scores to spreadsheets post-match.
  • Lack of Integration: Existing small-scale scoring apps do not link team management with equipment purchasing or global leaderboards.

1.5 ASSUMPTIONS AND CONSTRAINTS

  • Assumptions: Users have access to modern web browsers and an active internet connection for live scoring syncing. Waiters/scorers have basic knowledge of cricket rules.
  • Constraints: Heavy dependency on network stability during live scoring; offline fallbacks may have limited capacity in initial versions.

1.6 ADVANTAGES OF THE PROPOSED SYSTEM

  • Centralized Data Hub: All teams, matches, tournaments, and purchases reside in a single, secure MongoDB cluster.
  • Real-Time Accuracy: Programmatic calculations of complex cricket metrics instantly.
  • Digital Ecosystem: Unites the supply chain of playing the game (scoring/teams) with equipping for the game (apparel/gear).
  • Stunning UI/UX: Built with Radix UI and Framer Motion, offering dynamic transitions, skeleton loaders, and a highly responsive experience.

1.7 LIMITATIONS OF THE PROPOSED SYSTEM

  • Initial version requires active internet architecture – no fully localized offline scoring engine.
  • Integrating external delivery tracking for e-commerce store is handled manually by admin until third-party logistics APIs are plugged in.

2. REQUIREMENTS GATHERING & TARGETED USERS

2.1 TARGET USERS

  1. Scorers & Umpires: Require an intuitive interface to immediately record complex game states seamlessly.
  2. Team Managers / Captains: Need a dashboard for drafting players, managing profiles, and tracking historical roster performance.
  3. Tournament Admins: Require God-mode access to schedule fixtures, modify match statuses, and finalize standings.
  4. Fans / Customers: Need read-only access to live matches, and dynamic purchasing access to the Pro Store for ordering gear.

2.2 REQUIREMENTS

Functional Requirements:

  • The system must provide secure user authentication (Registration, Login, Role assignment).
  • The system must allow users to create and manage teams, including adding players, assigning roles, and uploading team logos.
  • The system must feature a live scoring engine to log runs, extras, wickets, and compute rates per ball.
  • The system must be capable of generating match result summaries and sharing them (e.g., via generated PDF).
  • Users must be able to browse a catalog of merchandise, add items to a cart, view a checkout sheet, and manage their order.

Non-Functional Requirements:

  • Performance: Live score updates should be persisted with minimal latency.
  • Usability: The UI must adhere to modern glassmorphic designs, with intuitive micro-interactions and dark/light modes.
  • Scalability: The NoSQL (MongoDB/Mongoose) schema must be capable of scaling from local tournaments to nationwide leagues.

  1. Scorer presses "4 Runs".
  2. UI local state updates instantly, firing API request `/api/matches/[id]/ball`.
  3. Server calculates updated OVS, Runs, Strike rate.
  4. Server responds 200 OK. Backend persists to MongoDB.

  3. `CartContext` checks existing Array.
  4. If exists, increment quantity. If new, push object to payload.
  5. User opens Sidebar Cart -> clicks Checkout -> Confirms Order -> DB `Orders` created.

4. DEVELOPMENT

4.1 CODING STANDARDS

  • Framework Architecture: Next.js 16 App Router paradigm with Server and Client Components appropriately isolated ("use client" declarations).
  • Naming Conventions: CamelCase for functions and variables, PascalCase for React Components (e.g. LandingHero.jsx), Kebab-case for module paths and URLs.
  • Modularity: Reusable UI components housed in components/ui/ (using Radix structural primitives combined with tailwind-merge class overrides).
  • State Segregation: Global concerns (Theme context, Cart context) wrapped in React Contexts, whereas local ephemeral state uses useState/useReducer.
  • Validation: Zod schemas applied globally before Mongoose hydration to prevent malicious payloads or bad schema imports.

5.5 RISK MANAGEMENT & CONTINGENCY PLAN

  • Risk: Internet failure during a Live Match scoring process leading to lost calculations.

  • Risk: Edge-case cricket rules (e.g., Penalty runs, run out on wide).
    Contingency: Form-based fallback modals for umpires to override algorithmically generated stats manually.
